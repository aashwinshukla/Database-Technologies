# Tables & Keys

## Tables
- Data in relational databases is stored in tables
- A table has columns (attributes) and rows (entries/records)
- Each column has a specific data type (INT, VARCHAR, DATE, etc.)
- Each row is one instance of that data

### Example — Student Table
| student_id | name  | major   |
|------------|-------|---------|
| 1          | Jack  | Biology |
| 2          | Kate  | Sociology |
| 3          | Claire | English |

## Keys

### Primary Key
- Uniquely identifies each row in a table
- Cannot be NULL, cannot be duplicate
- Every table should have one
- Can be a single column or a combination of columns (composite key)

### Surrogate Key
- A primary key with no real-world mapping
- Just an arbitrary unique value (e.g. auto-incremented ID)
- e.g. `student_id = 1, 2, 3...`

### Natural Key
- A primary key that has a real-world meaning
- e.g. Social Security Number, email address
- Generally less preferred — real-world values can change

### Foreign Key
- An attribute in one table that references the primary key of another table
- Used to link two tables together
- Enforces referential integrity — can't reference a row that doesn't exist

### Example
- `branch_id` in an Employee table → references `branch_id` in a Branch table
- That `branch_id` in Employee is a **foreign key**

### Composite Key
- A primary key made up of two or more columns
- Neither column alone is unique, but together they are
- Common in junction/linking tables (many-to-many relationships)

## Summary
| Key Type     | Description |
|--------------|-------------|
| Primary Key  | Uniquely identifies a row in its own table |
| Foreign Key  | References a primary key in another table |
| Surrogate Key | Arbitrary ID with no real-world meaning |
| Natural Key  | Has real-world significance (e.g. SSN) |
| Composite Key | Two+ columns together form the unique identifier |
