# ER Diagrams

## What is an ER Diagram?
- Entity Relationship Diagram
- A visual blueprint of a database
- Shows entities, their attributes, and how they relate to each other
- Used in the design phase — before writing any SQL

---

## Core Components

### Entity
- A real-world object or concept
- Represented as a **rectangle**
- e.g. Student, Employee, Branch

### Attribute
- A property of an entity
- Represented as an **oval**
- e.g. Student has: student_id, name, major

### Primary Key Attribute
- Attribute that uniquely identifies an entity
- Underlined in the diagram
- e.g. student_id

### Composite Attribute
- An attribute made up of multiple sub-attributes
- e.g. Full Name → first_name + last_name

### Multi-valued Attribute
- An attribute that can have multiple values
- Represented with a **double oval**
- e.g. an employee can have multiple club memberships

### Derived Attribute
- Value can be derived from another attribute
- Represented with a **dashed oval**
- e.g. age derived from birth_date

---

## Relationships

### Relationship
- A connection between two entities
- Represented as a **diamond**
- e.g. Employee **works for** Branch

### Total Participation
- All entities in the set must participate in the relationship
- Represented with a **double line**
- e.g. every employee MUST work for a branch

### Partial Participation
- Entities don't have to participate
- Represented with a **single line**

---

## Cardinality (Relationship Ratios)

| Type | Meaning |
|------|---------|
| 1:1 | One entity relates to exactly one other |
| 1:N | One entity relates to many others |
| N:M | Many entities relate to many others |

- Written on the lines connecting entities to relationships

---

## Weak Entity
- An entity that cannot be uniquely identified by its own attributes alone
- Depends on another entity (its owner) for identification
- Represented with a **double rectangle**
- Its relationship to the owner is a **double diamond**
- Has a **partial key** (dashed underline) — unique only within the context of the owner
- e.g. an Exam entity that depends on a Course entity

---

## Designing an ER Diagram — Example: Company

### Entities
- Employee, Branch, Client, Works_With, Branch_Supplier

### Relationships
- Employee **works for** Branch (many employees, one branch) → N:1
- Branch **managed by** Employee → 1:1
- Employee **works with** Client → N:M
- Branch **supplies** via Branch_Supplier → 1:N

### Steps to Design
1. Identify all entities
2. Identify attributes for each entity
3. Mark primary keys (underline)
4. Identify relationships between entities
5. Determine cardinality for each relationship
6. Mark total vs partial participation

---

## Converting ER Diagram to Schema

### Rules
1. **Each entity** → becomes a table
2. **Each attribute** → becomes a column
3. **Primary key** → PRIMARY KEY in the table
4. **1:1 relationship** → add foreign key to either side (usually the one with total participation)
5. **1:N relationship** → add foreign key to the N side (many side)
6. **N:M relationship** → create a new junction/bridge table with foreign keys from both sides
7. **Weak entity** → include owner's primary key as a foreign key + partial key → together form composite PK
8. **Multi-valued attribute** → create a separate table for it

### Example
- Employee (1) — works for — (N) Branch
  - Add `branch_id` as foreign key in `employee` table

- Employee (N) — works with — (M) Client
  - Create `works_with` table with `emp_id` and `client_id` as composite PK

---

## Notes
- ER diagrams are database-agnostic — not tied to MySQL or any specific system
- Great for planning before implementation
- Tools: draw.io, Lucidchart, MySQL Workbench (has built-in ER diagram tool)
- Always design the ER diagram before writing `CREATE TABLE` statements
