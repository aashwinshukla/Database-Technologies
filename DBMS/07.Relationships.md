# Relationships

## Cardinality
- Defines how many instances of one entity relate to instances of another
- Three types: 1:1, 1:N, M:N

---

## One to One (1:1)

- One instance of entity A relates to exactly one instance of entity B and vice versa
- e.g. One person has one passport, one passport belongs to one person
- e.g. One employee has one company car

### How to represent in schema
- Add a foreign key in either table (usually the one with total participation)
- Or merge both into one table if the relationship is very tight

### ER Diagram
```
[ Person ] ——1——<has>——1—— [ Passport ]
```

---

## One to Many (1:N)

- One instance of entity A relates to many instances of entity B
- But one instance of B relates to only one instance of A
- e.g. One department has many employees, but each employee belongs to one department
- e.g. One customer places many orders

### How to represent in schema
- Add the foreign key on the **many (N) side**
- e.g. add `dept_id` as FK in the Employee table

### ER Diagram
```
[ Department ] ——1——<has>——N—— [ Employee ]
```

---

## Many to Many (M:N)

- One instance of A relates to many instances of B
- One instance of B also relates to many instances of A
- e.g. One student enrolls in many courses, one course has many students
- e.g. One employee works with many clients, one client works with many employees

### How to represent in schema
- Create a **junction/bridge table** with FKs from both sides
- The junction table may also have its own attributes (e.g. `grade`, `total_sales`)

### Example
```
Student (student_id, name)
Course (course_id, title)
Enrollment (student_id FK, course_id FK, grade)  ← junction table
```

### ER Diagram
```
[ Student ] ——M——<enrolls in>——N—— [ Course ]
```

---

## Weak Entity

- An entity that cannot be uniquely identified by its own attributes alone
- Depends on another entity (called the **owner/strong entity**) for identification
- Represented with a **double rectangle**
- Its relationship to the owner is a **double diamond** (identifying relationship)

### Partial Key
- The attribute that partially identifies a weak entity within the context of its owner
- Shown with a **dashed underline** in ER diagram
- e.g. `room_number` is a partial key for Room — only unique within a specific Hotel

### Example
- `Hotel` (strong entity) owns `Room` (weak entity)
- Room cannot exist without a Hotel
- `room_number` alone is not unique across all hotels
- Together: `hotel_id + room_number` uniquely identifies a room

### How to represent in schema
- Include the owner's PK as a FK in the weak entity table
- Composite PK = owner's PK + partial key

---

## Participation Constraints

### Total Participation
- Every instance of the entity must participate in the relationship
- Represented with a **double line**
- e.g. every employee MUST work for a branch

### Partial Participation
- Entities are not required to participate
- Represented with a **single line**
- e.g. not every employee manages a branch

---

## Minimizing Tables (ER to Schema)

### General Rules
- 1:1 → merge into one table OR add FK to either side (2 tables min)
- 1:N → add FK to the N side (no extra table needed)
- M:N → always needs a junction table (3 tables minimum)
- Weak entity → include owner PK as FK + partial key as composite PK

---

## Notes
- M:N relationships always produce a new table when converting to schema
- Weak entities always depend on a strong entity for their existence
- Total participation = mandatory relationship, partial = optional
